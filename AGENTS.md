# AGENTS.md — DOOM3_AINative

An AI-native workspace for migrating DOOM 3 (idTech4, C++, OpenGL) to the web and for running an
agent-driven engineering loop around it: spec → worktree → PR → independent review → evidence.

The engine source is a **submodule**, not a copy. This repository owns the port, the automation,
the specs, and the workflow.

## Read first

| File | Why |
|---|---|
| `docs/GIT_WORKFLOW.md` | Issue → branch → worktree → PR → review → merge. One issue = one branch = one worktree = one PR. |
| `docs/SKILLS.md` | Which project skill to load for which stage, and where each skill came from. |
| `docs/ROADMAP.md` | Milestones, exit criteria, and what is actually proven vs suggested. |

## Repository facts

- `doom3_orig/doom3/` — **pristine** git submodule: `https://github.com/yhyu13/DOOM-3.git`
  (fork of `id-Software/DOOM-3`), the DOOM 3 GPL source release of 2011-11-22. License: GPLv3
  (`doom3_orig/doom3/COPYING.txt`). The source release contains **no game data**; assets remain
  under the original EULA (`doom3_orig/doom3/README.txt`). Native build reference:
  `doom3_orig/doom3/neo/doom.sln` (Visual Studio 2010, DirectX SDK).
- `doom3_orig/doc/` — engine analysis notes written against the pristine tree (evidence for the
  port; line numbers drift when the submodule is bumped).
- `targets/<name>/doom3/` — one **copy** of the pristine source per migration target, created by
  `scripts/new-target.ps1`. Copies are git-ignored scratch trees; a target never edits the pristine
  submodule or another target's copy. See `targets/README.md`.
- `.specify/`, `.kilo/command/speckit.*.md` — GitHub spec-kit, installed with the generic
  integration and PowerShell scripts.
- `.claude/skills/` — 25 tracked skills: 15 non-speckit (12 from the user's skill vault, 2 vendored from
  upstream MIT repositories, 1 written here for the Win64 port) plus 10 `speckit-*` skills. Real files,
  not junctions. This is the source of truth in git, and what Claude Code reads natively.
- `.kilo/skills/` — byte-identical, **git-ignored** mirror of `.claude/skills`, generated by
  `scripts/sync-skills.ps1` (also run by `.kilo/setup-script.ps1` for every Agent Manager
  worktree). Kilo discovers it as a project config directory. Never edit it by hand.
- `CMakeLists.txt`, `CMakePresets.json` — root build entry: `cmake --preset win11-amd64` (creates and
  patches the git-ignored target copy on first run) then `cmake --build --preset win11-amd64-release`;
  output `build/bin/Release/DOOM3.exe` and `build/bin/Release/DOOM3XP.exe` (d3xp game code statically
  linked; needs retail RoE data to play, runs the base game only via `DOOM3.exe`; retail RoE gameplay is
  unverified). `build/` is per worktree and git-ignored. Pass MSBuild switches as `-- -m` (Git Bash
  mangles `-- /m`).
- Engine diagnostics added by the port: console commands `sys_cpuInfo`, `sys_fpuState`, `sys_stackTrace`;
  `SAVEGAME_VERSION` is 18 (older saves are rejected with a warning). Tests (`-Exe -DataDir -OutDir`,
  net test also `-Port`): `scripts/test-cpu-fpu-trace.ps1`, `test-savegame-demo.ps1`,
  `test-net-loopback.ps1`, `test-d3xp.ps1`.
- `scripts/` — workflow helpers (worktrees, target copies, skill verification).

## Non-negotiables

1. **The pristine submodule is read-only.** Never edit `doom3_orig/doom3/` in place. Engine changes
   belong on a branch of the fork; land it there, then bump `doom3_orig/doom3` here
   (`git add doom3_orig/doom3`) with the new SHA in the PR body. Migration work happens in
   `targets/<name>/doom3`, which is never committed. Unexplained submodule dirt is a review blocker.
2. **One copy per target.** Do not share a target copy, and do not edit one target from another
   target's session. Create a copy with `scripts/new-target.ps1 -Name <target>`.
3. **Never commit game data or build output.** `.pk4`/`.pk3`/`.pak` assets, binaries, object
   files, and per-worktree build directories stay out of git. GPLv3 covers the source only.
4. **No direct commits to `main`.** No force-push to `main`. No `git stash` — stashes are shared
   across worktrees and silently corrupt parallel work.
5. **Evidence before victory.** A task is done only when a command's output proves it: build exit
   code, test summary, screenshot, or file listing. Load the `verification-before-completion`
   skill before claiming completion.
6. **No secrets or machine-specific absolute paths** in tracked files. Use environment variables
   and paths relative to the repository root.
7. **One writer per file.** Parallel agents must not edit the same file; split by ownership
   (see `docs/GIT_WORKFLOW.md`).
8. **Merge only into a clean, current `main`.** Before merging a PR, check the target mainline
   itself, not just the remote verdict. `git fetch origin`, then `gh pr view <N> --json
   mergeable,mergeStateStatus` must report `MERGEABLE` / `CLEAN`, **and** `git status
   --porcelain` in the main worktree must show no modified (unstaged), staged or untracked file
   that the PR touches — the mergeability flag is computed from the remote head and cannot see
   local dirt. Prove the merge offline with
   `git merge-tree $(git merge-base origin/main origin/<head>) origin/main origin/<head>` and
   grep for a header line starting with `changed in both` (`grep '^changed in both'` — the command
   exits 0 even on a conflict, and an unanchored grep also matches the phrase inside patched file
   content). Clear the overlap first: a dirty main worktree is a merge blocker, not something to
   work around.
9. **Start from `main`, or stop.** New work starts on `main`. Before touching a file, check
   `git branch --show-current` (and `git worktree list` when the path is under `.kilo/worktrees/`).
   If the checkout is not `main` and the user did not name a branch or a worktree, stop
   immediately and ask which one to use. A task description is not permission to continue on
   whatever branch happens to be checked out, and not permission to commit to it. A detached
   HEAD counts as "not `main`".
10. **Never close an issue without the user's permission.** Do not run `gh issue close`, and do
    not write `Closes #N`, `Fixes #N` or `Resolves #N` in a PR body or commit message, unless the
    user explicitly approved closing that issue. Link with `Refs #N`. A merged PR proves the work,
    not the decision to close the issue; say the work looks finished and let the user decide.
    This supersedes the `Closes #N` wording in `docs/GIT_WORKFLOW.md` and `CONTRIBUTING.md`.

## Spec-driven flow

```
/speckit.constitution  → establish project principles (required once, then edit by PR)
/speckit.specify       → specs/<feature>/spec.md
/speckit.clarify       → resolve ambiguities before planning (optional but recommended)
/speckit.plan          → specs/<feature>/plan.md
/speckit.tasks         → specs/<feature>/tasks.md
/speckit.analyze       → cross-artifact consistency check (optional)
/speckit.implement     → execute tasks
/speckit.converge      → append remaining work as tasks
```

Artifact paths and exact filenames are produced by `.specify/scripts/powershell/*.ps1`; read
`.specify/templates/` rather than guessing. Do not skip `/speckit.plan` for anything that touches
the engine build, the renderer, or the submodule.

## Working in a worktree

Agent Manager runs `.kilo/setup-script.ps1` for every new worktree, which initialises
`doom3_orig/doom3/`. For a hand-made worktree run `git submodule update --init --recursive` inside
it. Target copies (`targets/<name>/doom3`) are not part of git; recreate them in a new worktree
with `scripts/new-target.ps1 -Name <target>` instead of copying them between worktrees. Build
directories, caches, and ports must be derived from `WORKTREE_PATH`; never share them.

## Skills

Skills exist in two places, and the difference matters:

| Path | Tracked in git | Who reads it | How it is produced |
|---|---|---|---|
| `.claude/skills/<name>/SKILL.md` | **yes** — source of truth | Claude Code, natively | edited by hand (or copied from the vault) |
| `.kilo/skills/<name>/SKILL.md` | no — ignored by `.gitignore` | Kilo, as a project config directory | `scripts/sync-skills.ps1` only |

Both trees must hold the same 25 skills, byte-for-byte. `scripts/verify-skills.ps1` enforces that:
it validates the Claude skill format of every tracked skill (`name` == directory, lowercase
kebab-case, `description` <= 1024 chars) and fails when the mirror is missing, stale, or holds
extra files. To change a skill, edit `.claude/skills` and run the sync; never edit the mirror.

`kilo.json` also lists `./.claude/skills` under `skills.paths`. That path was **observed not to take
effect** in a VS Code session whose workspace root was above the project directory, which is exactly
why the generated `.kilo/skills` mirror exists — it does not depend on `kilo.json` being applied.
Treat `skills.paths` as a convenience, not as the mechanism.

Port know-how (`win64-port-playbook`: Windows x64 bring-up, debugging loop, bug catalogue) sits in
the same tree. The skills mirror the user's global vault at `~/.kilo/skills`; the project copy is
authoritative inside this repository. The stage map, source paths, pinned upstream commits, and the
"not installed and why" list are in `docs/SKILLS.md`. Contributor rules for humans and agents:
`CONTRIBUTING.md`.

Port know-how lives in `.claude/skills/<name>/SKILL.md` (currently `win64-port-playbook`: Windows x64 bring-up,
debugging loop, bug catalogue). `kilo.json` lists that directory under `skills.paths` so Kilo agents see it;
other harnesses read `.claude/skills` natively. Contributor rules for humans and agents: `CONTRIBUTING.md`.

Do not add a skill that duplicates an installed one. If a vendored skill needs local changes, copy
it to a new name and document the diff instead of editing it in place.
