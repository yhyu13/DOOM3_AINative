# Contract: RHI foundation and first executable seam

**Status**: Design for incremental implementation; no operation is available until implemented and tested.

**Scope**: A backend-neutral RHI boundary and a data-independent D3D12 vertical slice. This does not define a game renderer or claim completion of the full Q1 gate.

## Two tiers and the engine adapter

The **portable core** is a deliberately bounded, WebGPU-subset-oriented logical contract: it is designed to be implementable over WebGPU, not a statement that every operation, format or limit below is supported by any browser. The same eventual ordered engine adapter targets this core; separate native D3D12 and future web WebGPU backends lower it independently. The adapter does not wrap individual GL calls and never accepts a D3D12 handle. A core operation is usable on a target only after that target implements it, probes/enables the required capability and limits, and passes its own tests. Q1a exercises only the first seam below, not the full core or portability.

An **optional native extension tier** exposes individually negotiated, backend-specific functionality through a separate interface. Native interop, provider calls, DXR, multiple queues and bindless access are not core operations or implicit device features. A native backend may implement the core without any extension. Extension presence, enabled features and actual execution are separate facts. Neither a native D3D12 run nor this design establishes a web backend, WebGPU DXR/DLSS, shader translation, a WASM retail-data fit, or performance.

## Portable core semantics

These are requirements for later slices, not operations promised by Q1a. Exact function names are implementation choices.

1. **Selection and lifecycle.** The caller explicitly selects a backend and adapter class, requests a set of required and optional features/limits, and receives either a device with its *enabled* capability profile or an actionable error. Never silently change backend, adapter or rendering mode. A device owns its resources, bindings, pipelines and submissions; handles identify both device and generation. Cross-device, stale or destroyed handles fail validation. Destruction invalidates a client handle immediately, but backend objects and recorded references survive until their last submitted use retires; incomplete initialization and shutdown are safe. Device loss makes outstanding operations fail rather than appear complete; recovery/recreation is an explicit higher-level decision.
2. **Descriptions and limits.** A resource description declares dimension, extent, format, mip/layer/sample counts, permitted usages and lifetime. A view selects an in-range subresource and compatible format/use. The enabled profile reports actual per-target format/use combinations, dimensions, alignment, buffer sizes, binding counts, attachment counts and other limits used by a requested operation; creation validates against those limits. No numeric common floor or exact WebGPU feature set is asserted before target execution. The first slices use no aliasing.
3. **Usage and bindings.** A buffer or texture is created with the union of intended copy-source, copy-destination, sampled, storage, vertex/index, uniform, attachment or readback uses as applicable. Every layout entry has a **(bind-group index, binding index)** pair, resource type, access, shader-stage visibility, minimum range/alignment and array count. Each pair is unique within the pipeline layout; validate both indices, group count, per-group and per-stage binding counts, dynamic offsets, ranges, alignment, types, visibility, array features and all other applicable enabled limits against the actual target. Bindings must match the layout and declared usages. A native lowering may map the pair to native registers/spaces or descriptors only through a deterministic collision-free mapping reflected in the shader and pipeline; reject an unrepresentable mapping. A later read observes an earlier write only after the declared dependency/order. The frame graph cannot silently assume safe aliasing or synchronization.
4. **Recording and submission.** A command recording retains all referenced objects; its declared accesses and pass dependencies establish write/read ordering. The backend lowers logical usage changes and ordering to its own transitions/barriers; the caller is not given D3D12 resource states as the portable API. Closing and submitting a valid recording yields a device-scoped completion token. One ordered logical queue is the core baseline; submission order and dependencies define visibility. Never-submitted or aborted recordings release their recorded references on reset, without manufacturing a completion token or retiring submitted work. Submitted resources, binding allocations, upload/readback storage and command recording storage cannot be reused or released until the backend proves the last submitted use has ended.
5. **Completion and readback.** Completion is observed asynchronously through polling or a callback/future with success, failure/device-loss or cancellation; no unbounded synchronous wait is required by the portable API. A successful completion may prove retirement and makes prior submitted writes available to the next ordered use or the completed readback operation, subject to its declared access. Failure, cancelled observation or device-loss notification alone is not proof that GPU use has ended. If proof is unavailable after loss, quarantine affected allocations from reuse until a backend-defined, documented teardown guarantees their use has ended; otherwise report cleanup incomplete. This cleanup is not successful completion. A readback is requested from a copy-capable resource into appropriate staging storage, and its bytes are made available only after the producing submission and asynchronous mapping/copy complete. Expose caller-owned copied bytes with explicit extent, format and tightly packed stride, or a separately documented bounded mapped-view lifetime; unmap/reset invalidates that view. Backend staging row pitch, alignment and padding are not assumed to equal the caller stride. Cancellation and shutdown cannot publish incomplete bytes.
6. **Browser scheduling.** Device acquisition, completion, mapping and errors may complete asynchronously. Browser main-thread clients must yield to the event loop; they must not depend on a busy wait, blocking fence wait, or immediate mapping. A native-only fixture may use a bounded/blocking wait for its Q1a fence, but that wait is not a core requirement. No browser implementation is implied.
7. **Failure and fallback.** Validate descriptors, usage, bindings, limits and ordering before submission where possible; report stage, operation, target and a stable category such as `unsupported`, `invalid-usage`, `out-of-memory`, `device-lost` or `backend-error`, with backend diagnostics when available. Errors discovered asynchronously are associated with the affected request/submission and surfaced to the caller; they cannot be converted to success. When a requested operation is unsupported, return `unsupported` with the missing requirement. The caller may explicitly select a separately available fallback and must record the selection and reason; no automatic switch is promised. Failure to initialize the new engine path leaves the existing GL path selectable and usable once that integration is implemented and tested.

### Conservative usage-scope subset

This proposed subset is informed by [WebGPU resource usages and usage scopes](https://www.w3.org/TR/webgpu/#programming-model-resource-usages); it is deliberately narrower, not a claim of WebGPU conformance. Apply it on native as well as any future web implementation; native barriers alone do not make an invalid portable scope legal. Validate every declared use against creation, view/range, profile and scope rules. Return `invalid-usage` for a conflicting declaration and `unsupported` for an operation outside this subset or not supported by the target; do not silently permit it.

- A usage scope tracks a **whole buffer**, even when views or byte ranges do not overlap; texture scopes track the underlying texture subresource (mip, array layer and aspect), not just view identity. Views covering the same subresource conflict even if their rectangles differ. Reject same-resource self-copy in this subset; copies use distinct, compatible resources, and each copy is a separate operation outside render/compute passes. A mapped buffer must not be used by submitted GPU work until unmapped.
- One **entire render pass** is one scope. Include attachments and all resources referenced anywhere in the pass, including bind groups and vertex/index buffers set then replaced or never drawn, and direct/indirect draw resources. Splitting conflicting use across draws or inserting a native barrier inside the pass does not split the scope; end it and start a new ordered pass.
- Each **compute dispatch** is its own scope, not the entire compute pass. Include all resources potentially accessible through bind groups required by the current pipeline layout and any indirect dispatch buffer; state-setting alone does not create a dispatch scope. Separate ordered dispatches can change uses only where the backend provides the required dependency and visibility.
- Within one scope and underlying subresource, allow multiple read-only bindings/uses only when each target supports the combination. Alternatively allow a single write-capable binding or attachment, with no other binding/use of that subresource in that scope; repeated draws through that same binding/attachment are not additional bindings. A read/write storage binding counts as write-capable. Do not assume distinct buffer ranges or texture views avoid a conflict. This intentionally rejects some WebGPU-compatible combinations; unsupported format/aspect or usage combinations remain unsupported. Pass/dispatch boundaries do not eliminate the need for correct ordering and backend transitions.

## Capability and fallback matrix

The table defines *selection policy*, not observed capabilities. `Core` means intended portable contract, not present or guaranteed; `Native extension` means outside it. An alternative is selectable only if separately implemented, enabled and tested on that actual target. Otherwise return `unsupported`; none switches automatically. Each target records requested, advertised, enabled and actually executed features and limits independently.

| Operation | Tier | Capability / limit to check | Explicit selectable fallback or unsupported | Evidence required |
|---|---|---|---|---|
| `core-device` | Core | Backend/adapter, required enabled features and limits | Select another available adapter or backend explicitly; otherwise `unsupported` | Actual target selection and failure tests |
| `core-resources-bindings` | Core | Format/usage, dimensions, alignment, group and binding indices, per-group/per-stage counts and shader visibility | Explicitly choose a compatible format, smaller layout or supported path; otherwise `unsupported` | Target resource, pair mapping, usage-scope and limit tests |
| `core-submit-readback` | Core | Ordered queue, copy uses, staging alignment and async completion | Explicitly select an implemented path without readback if acceptable; otherwise `unsupported` | Target ordering, retirement and readback tests |
| `core-draw-compute` | Core | Pipeline/shader stages, attachments, storage uses and actual limits | Select an implemented simpler draw/compute or compatibility path; otherwise `unsupported` | Target-specific shader, draw and compute tests |
| `core-present` | Core | Surface availability, format, size and presentation support | Select implemented offscreen output if appropriate; otherwise `unsupported` | Actual target surface/resize tests |
| `native-interop` | Native extension | Backend-specific bridge, permitted resources and ownership | Use core operations without native handles; otherwise `unsupported` | Backend-specific state and lifetime tests |
| `native-provider` | Native extension | Authorized provider, actual API/SDK, inputs, hardware and legal clearance | Explicitly select the independent reconstruction/off path; otherwise `unsupported` | Actual provider create/evaluate plus off-path and distribution review |
| `native-dxr` | Native extension | Actual native backend and ray-tracing capability | Explicitly select the implemented non-path-traced renderer; otherwise `unsupported` | Actual RT scene and fallback tests |
| `native-multi-queue` | Native extension | Queue creation, cross-queue ordering and retirement | Explicitly select the single ordered core queue; otherwise `unsupported` | Cross-queue hazard and lifetime tests |
| `native-bindless` | Native extension | Backend-specific descriptor indexing, binding and residency limits | Explicitly select implemented bounded bindings; otherwise `unsupported` | Target descriptor bounds and lifetime tests |

### Native interop and provider boundary

Native handles never cross the portable core. A separate opt-in extension may hand a native backend/provider a restricted, time-bounded lease after validating backend, device, resource identity, subresource, declared input/output access, required initial/final states, queue ownership, synchronization and authorization. The bridge retains the resources throughout the lease and outstanding submitted work; the recipient must not retain handles outside the agreed window. On return, report actual state/ownership and invalidate or restore affected backend caches before further core work. Failure or device loss is explicit; no unverified state is silently assumed. The concrete provider ABI, queue handoff and legal/distribution obligations remain unconfirmed until the actual authorized SDK is reviewed; an unavailable provider is NOT RUN. Multi-queue and bindless are separate opt-in extensions, not incidental privileges of a provider.

## Shader source, build and validation contract

- **Inputs and rights**: A fixture starts with project-authored synthetic shader source or other source whose origin, version/hash, license, modification/translation permission, distribution permission and permitted local use are recorded. Retail `glprogs`, game data and derived shaders are not assumed present, translatable or redistributable. If a right is unresolved, do not perform or distribute the affected transformation; record the missing permission and mark that stage NOT RUN.
- **Discovery and identity**: Discover installed or separately authorized compilers/validators without automatic proprietary downloads. Record executable identity/version, target language/profile, options, entry points, defines, includes and their identities, binding layout, toolchain configuration and command/exit. A missing compiler or target is an explicit unavailable/unsupported result, not a successful compile.
- **Pipeline**: For each authorized source and selected target, record source → any separately authorized preprocessing/translation → target-specific compilation → validation → pipeline/layout creation → actual target execution/readback. A target may use separately authored permitted source instead of translation; the chosen path and its inputs must be explicit. Record inputs, intermediate/output identities and failure stage/diagnostics. No translator or exact language mapping is assumed to exist. A target artifact is usable/distributable only within the recorded permissions; do not track restricted source, derived data or binaries.
- **Bindings and target proof**: Compare declared (bind-group index, binding index) pairs, types, access, stage visibility and resource limits with each target artifact and pipeline layout; validate the collision-free native mapping and reject mismatches. Record compiler/validator messages and the target device/browser/version when actually run. Native HLSL/DXC compilation or a translated artifact does not prove WebGPU compilation, pipeline creation, rendering or a browser port. Each claimed target needs its own validation and real-scene evidence.

## Public boundary

The first executable boundary is a small C++ API that lets a client:

1. Select an explicitly named adapter class (hardware or software), create a device and observe a meaningful unsupported/error result.
2. Create an explicitly described 2D colour resource and record a clear plus a transfer to a readable CPU result.
3. Submit the commands, wait for their fence and inspect the resulting pixels. The caller owns neither native COM objects nor backend descriptor internals. This native Q1a fixture wait is not a portable browser requirement.
4. Release client handles and shut down safely, including after incomplete initialization; GPU-owned objects, command allocators and upload/readback storage remain alive until their submitted work completes.

Exact function names are implementation choices; tests must use the same public boundary that an eventual renderer client uses. The backend-specific implementation owns D3D12/DXGI types. Do not add speculative operations merely to make the interface look complete.

## First vertical-slice acceptance

- Configure/build the standalone fixture without the engine target copy, game data or proprietary NVIDIA SDK. The installed Windows SDK and Visual Studio C++ tools are required.
- On an available explicitly selected adapter, clear a synthetic RGBA8 texture using a **per-row distinct pattern** (at least two rows differ, and the row index is recoverable from the expected bytes), read it back, and compare every row against independently specified byte values. Expected values are derived by the test from the pattern definition, never from the renderer's output. Allow only the documented UNORM rounding tolerance.
- Account for D3D12 readback row pitch. A tightly packed CPU output stride of `width * 4` is valid; that is not the same as the GPU staging footprint's row pitch. Include three negative controls that must fail: (a) using `width * 4` as the staging row stride when the returned row pitch is larger, (b) an off-by-one source-row offset, and (c) repeating row 0 for every row. If a control is genuinely inapplicable on a conforming implementation, record it as NOT APPLICABLE with the reason; do not count it as a pass.
- Declare and implement the Q1a state sequence rather than leaving it implicit: the colour resource is created for render-target use, cleared in `RENDER_TARGET`, transitioned to `COPY_SOURCE`, and the readback buffer is in `COPY_DEST`. The backend keeps a state journal for the resource and a test asserts the recorded sequence. A general public transition API remains Q1b work, but the Q1a implementation must perform the correct transitions.
- Submit at least two independent submissions. At least one release/reset attempt must occur while its submission fence is still unsignalled: assert `GetCompletedValue() < signalValue` at the moment of release. A test that waits idle before every release is not evidence. Use a controlled gate or a deliberately long command so the outstanding condition is deterministic, and include a negative control that shows the test fails if the wait-idle shortcut is used.
- Readback results cross the public boundary as caller-owned bytes copied after the producing fence signals. If an implementation instead exposes a mapped view, the public contract must state a single validity window and a test must prove it; a raw pointer with unspecified lifetime is not acceptable.
- Report hardware versus software adapter and the check result. Attempt each adapter class that is present; at least one adapter must actually execute the clear/readback test. Adapter unavailability is SKIPPED/NOT RUN, not PASS. A software run is a functional check, not hardware performance evidence.
- Debug layer and GPU-based validation: the fixture must expose opt-in requests, attempt enablement, capture messages into the retained test log, and record absence/failure distinctly. Reporting "unavailable" without attempting enablement is not evidence. Debug-layer and GPU-based validation are separate from functional execution and must not be marked passing without actually running.
- Retain the full CTest log (`-V` or `--output-junit`/`--output-log`), including successful test output, adapter identity and executed/skipped checks. `--output-on-failure` alone retains only failures.
- Failures expose an actionable stage/error; device creation alone is not counted as a successful rendering or readback test.

This is **Q1a**. Passing it does not complete Q1, User Story 2 or the programme's success criteria.

### T013 row-hash and tolerance policy

The proposed reconciliation preserves issue #11's independent per-byte acceptance: fix the per-channel UNORM tolerance at **absolute integer difference ≤ 1** before the run, and compare every actual byte against independently specified expected bytes. Values outside that bound fail. Before execution, publish the synthetic input pattern, independently derived canonical expected RGBA8 bytes for every row, hash algorithm, byte order, exactly `width * 4` bytes per row excluding staging padding, and an independently predeclared expected digest for each row. The test hashes each canonical expected row and compares it to its corresponding predeclared digest; a mismatch fails the expected-data integrity check. A reviewer must be able to recompute those digests independently from the published bytes without reading renderer output.

Also log the raw digest of each actual tightly packed row for diagnosis, but **do not require actual and expected digests to match**: even a permitted one-step byte difference normally changes the raw digest. Do not normalize or relabel actual hashes as expected-byte checks. Exercise a controlled one-step difference that passes the byte criterion and a two-step difference that fails it; use a sufficiently distinct row pattern to make the wrong-stride, off-by-one-row and repeat-row-0 controls detect the independent byte comparison. Those three controls remain required, with genuine inapplicability recorded rather than passed.

This policy changes the previous ambiguous task wording, not the higher-level spec or issue #11's per-byte acceptance; it requires independent review before T004/T013 acceptance. No Q1a implementation or result is asserted to satisfy it here.

## Foundation growth required for full Q1

After Q1a, extend the same boundary by independently tested slices for draw/pipeline and shader compilation, compute dispatch, multiple colour attachments, shader-readable depth, motion/validity and overlay resources, a general public transition/UAV-ordering API (beyond Q1a's internal clear/copy transitions), frame slots, resize, persistent history/reset and diagnostics. Before declaring Q1 complete, run zero-unwaived-error debug-layer and GPU-based-validation checks on an environment where those checks actually execute.

The frame graph consumes declared resource accesses and pass dependencies; it is not a facade that hides synchronization or assumes an aliased resource is safe. Device/queue/resources are not tied to deferred shading or an optional provider. Native-provider access is a restricted, explicitly declared boundary with resource states and state-cache invalidation/restoration, and is deferred until an actual authorized SDK contract is available.

## Compatibility and integration boundary

The planned engine adapter consumes the ordered view/set/copy/present command stream, not a wrapper for every historical `gl*` call. Commands can flush within a frame for screenshots/copies as well as at the normal end of frame. Classify display overlays, world GUIs and other 2D views by semantic purpose and preserve ordering/capture behavior; do not assume every 2D view can be moved to the final HUD pass.

The standalone component lives in this repository. Changes to engine-owned code follow the fork/submodule review path; target copies are scratch and are not a durable delivery mechanism. The patch exporter reproduces modified files only: added and deleted files become manifest rows with no hunks. `apply-target-patches.ps1` refuses a stored manifest containing such rows (unless `-AllowIncomplete`, which still reports failure), and `verify-win11-amd64.ps1` fails `SC-006b` when the manifest it exports contains one. That export derives both the patch and its expected hashes from the current target copy, so a passing `SC-006b` proves the copy against itself, not against the stored canonical patch: it cannot detect a required tracked modification that is missing from that copy. T084 owns closing that gap, and until it is closed a passing verifier is not evidence that the target equals the canonical patch. Deliver added or deleted files through the fork/submodule path instead of relying on the target-copy patch.

## Later renderer invariants

- Logical resource references carry explicit use and lifetime; native pointer values are not stable entity identities.
- Per-view history uses previous rendered state and a separate validity result. Main-view history cannot be committed by a mirror, shadow or security-camera view.
- A private previous skinned-pose copy survives the engine's shared dynamic-model cache updates and deletion.
- Scene reconstruction/provider input excludes the native-resolution display overlay; world GUI treatment remains a tested scene policy.
- Optional neural evaluation never becomes a hard-coded RHI operation or a dependency of the default renderer.
- Any future backend must implement and test its own capability/fallback table. Backend-neutral descriptions are not evidence of a browser or Vulkan port.
